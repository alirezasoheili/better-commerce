# M2 runtime plugin platform: Wasmtime components and explicit commerce extension points

Better Commerce will add a post-M1 runtime plugin platform that preserves the modular-monolith commerce core while allowing precompiled extensions to be installed without rebuilding the BC executable. Plugin backends are WebAssembly Components hosted in-process by Wasmtime; WIT is the canonical plugin ABI. Rust is the supported V1 authoring language, but the Component Model keeps the ABI language-neutral. Plugin UI remains ordinary built web assets served by BC, not WASM.

This decision intentionally supersedes the long-term assumption in ADR 0001 that installation reconciliation need not support runtime plugin activation. It does **not** reopen M1: ADR 0004 and the M1 specification remain authoritative for M1 and their runtime-plugin deferral remains part of that milestone's contract. M2 extends the platform after M1 rather than changing the M1 ticket graph.

The plugin boundary is separate from the bounded-context module boundary of ADR 0002. Core modules continue to own their data, domain invariants, application APIs and extraction seams. Only BC core defines plugin extension points. Plugins may participate synchronously only through explicit host-defined provider/contributor contracts; there are no generic global hooks and no plugin-to-plugin dependency mechanism. Each extension point declares cardinality (`single-provider` or `multi-contributor`), ordering where applicable and failure semantics.

V1 plugins are trusted first-party software. The platform does not implement marketplace publisher trust, signatures, OAuth between host and plugin, hostile-plugin permission approval or per-plugin capability policy. Wasmtime still provides a stable ABI boundary and fault containment. One long-lived component instance is active per plugin and V1 serializes all invocations for that plugin. Timeout/trap recovery discards the instance, recreates it and reruns `initialize()`. Repeated failures may open a simple circuit breaker. BC startup never fails merely because one plugin is broken; that plugin becomes unavailable.

A plugin release is one SemVer package with a stable plugin ID, immutable `plugin.yaml`, optional `backend.wasm`, optional migrations, optional built UI and package assets. Local-package install validates and copies the package into BC-managed storage and records desired enabled state. Install/upgrade/remove package changes are restart-bound; enable/disable and configuration changes are live. Activation performs compatibility validation and pending migrations, then—when a backend exists—instantiation, initialization and health before registration. Backend-less/UI-only plugins skip WASM lifecycle/health. Normal uninstall preserves plugin data; destructive removal is explicit. Failed upgrades do not auto-rollback.

PostgreSQL remains authoritative and BC retains one `sqlx::Pool`. WASM plugins access persistence through host DB APIs instead of owning independent database credentials/pools. Plugin migrations own plugin schema objects and may reference core keys, but may not alter core tables or add core-table triggers. Trusted V1 plugins may directly read core tables and therefore declare compatibility with the BC schema they target. Arbitrary direct SQL mutation of canonical core state is not the supported contract: core mutations use BC domain host APIs so state machines, invariants, idempotency, snapshots and outbox behavior remain core-owned. Plugin transactions never implicitly join an existing core transaction.

ADR 0003's transactional outbox guarantees remain intact. Core events are committed before plugin handling and are delivered at least once to plugins by direct WASM invocation through a PostgreSQL-backed durable execution system. Per-aggregate ordering is preserved while unrelated aggregates may advance. The same durable worker substrate handles plugin jobs and schedules with retries, backoff, leases, dead-lettering, manual retry, optional TTL, cancellation of queued work, simple ordered chains and static recurring schedules. No Redis/message broker or general DAG/workflow engine is required.

Plugin web UI is served under `/extensions/{plugin-id}/*`; plugin authenticated APIs use `/extensions/{plugin-id}/api/*`; public/provider callback routes use `/plugins/{plugin-id}/*`. BC authenticates requests and passes a stable `PluginContext`. BC owns large-file upload/download streaming and may expose generic host-owned SSE such as job progress; plugin-owned long-lived SSE handlers are excluded from V1 because invocations are serialized. Trusted plugins receive standard WASI outbound HTTP/HTTPS, TCP, UDP, DNS and clocks, but no arbitrary host process execution or host-wide filesystem access.

Commerce authority remains in BC. Payment, pricing, shipping, checkout fields, SEO/head metadata, sitemap, robots and redirect behavior are expressed as explicit typed extension points. Pricing contributors return structured adjustments rather than overwriting totals. Payment plugins map provider behavior into BC-owned purchase/payment identities and state transitions; provider operations that may have succeeded before a crash are treated as indeterminate and recovered with stable operation/reference identities rather than blind retry.

The complete contract, lifecycle, package descriptor, WIT boundaries, implementation roadmap and reference-plugin acceptance criteria are defined by `docs/specs/m2-runtime-plugin-platform.md` and the supporting files under `docs/plugin-platform/`. The architecture is considered proven only when realistic payment, dynamic pricing, SMS/event/job and UI/data reference plugins pass integrated restart/failure/compatibility tests.
